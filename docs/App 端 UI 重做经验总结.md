# App 端 UI 重做经验总结

> 日期：2026-09-17　|　范围：`frontend-app/`（安卓端）登录页与智能问答页
> 结论一句话：**"这个页面很丑"里通常没有配色问题——本例的病根是 Web 端两栏布局砍成一栏后留下的布局化石，以及一套写了却没用满的设计令牌。**
> 相关文档：`docs/Android App 打包与运行说明.md`（第 7.6 节 adb 操作命令、第 7.8 节未复现现象）

---

## 1. 背景与诉求

用户在模拟器上跑完 App 后提了三条：

1. 登录页和问答页"不够现代化"，要再优化；
2. 登录页最上方要有「宝智审」logo；
3. 登录页下方要有普通用户与专家用户的账号密码复制粘贴区域。

第 3 条看起来最简单，实际是这次唯一一处**需要先做取舍**的地方——原来的演示账号区块用
`import.meta.env.DEV` 守着，而装进模拟器的是生产构建，所以它**根本不渲染**。用户看到的截图里
没有这块，不是样式问题，是它被编译掉了（见第 6 节）。

设备参数先记下来，后面所有像素数值都基于它：**1080×2400，dpr 2.625，CSS 视口 411×914**。

---

## 2. 诊断：为什么"丑"不是配色问题

先读代码再动手。`src/styles/tokens.css` 里其实有一整套完整且有辨识度的设计：
纸色 `--paper: #faf8f5`（`tokens.css:14`）、印章朱红 `--accent: #b3342a`（`tokens.css:28`，
注释还标了对比度 6.10:1）、宋体标题、发丝分隔线，以及一层 SVG 噪点纸纹 `--grain`（`tokens.css:98`）。

问题是登录页**一样都没用上**。逐条对照代码与截图：

| 症状 | 代码依据 |
| --- | --- |
| 整屏死白，纸色纸纹全不见 | `.panel { background: var(--surface) }`——`--surface` 是纯白 `#ffffff`，把 `body` 上的 `--paper` 和 `--grain` 整个盖住了 |
| 表单悬在半空，下方一大片空白 | `.panel { display: flex; align-items: center }` 把表单垂直居中，而本该出现在表单下方的演示账号区块被 `import.meta.env.DEV` 编译掉了（见第 6 节），于是"居中"变成了"悬空" |
| 纯白页顶端有一条孤零零的发丝线 | `@media (max-width: 900px)` 分支给 `.panel` 加了 `border-top`。手机上 CSS 视口只有 411px，这个分支**必然命中**，但它当初是给两栏布局的分隔线写的 |
| 全页没有任何品牌标识 | 全工程唯一的品牌资产是 `public/favicon.svg`（朱红方印 + 「合」），而且**没有任何组件引用它** |

最能说明问题的是几条残留的布局化石：`.login-page` 是 `display: grid` 配 `grid-template-columns: 1fr`
的单列 grid，`.panel-inner` 上留着 `max-width: 380px`（手机端又被 `max-width: none` 覆盖掉），
以及那条注定命中的 `border-top`——全是为两栏布局写的，砍成一栏后没人回头收拾。

最有价值的线索是一条注释。原代码里写着：

```css
/* 屏窄放不下左侧定调面板，登录页只有表单一栏 */
.panel { display: flex; align-items: center; background: var(--surface); }
```

**这类措辞（"只保留…"、"屏窄放不下…"）值得当成缺陷标记来读**：它说明这段代码是在删东西时改出来的，
而删的时候只保证了"能显示"，没有重新设计剩下的那一栏。这比任何一个具体样式都更能解释"为什么丑"。

> **方法论**：把"丑"拆成**配色 / 布局 / 层级 / 品牌**四类分别定位。本例四类里三类有问题，唯独配色是好的——
> 如果一上来就换配色，等于把唯一做对的东西也推翻，而真正的病根（布局化石）仍然在。

## 3. 设计决策：深化而不是换皮

诊断完有两个方向：换一套更"现代"的皮，或者把已有语言用满。选了后者，理由：

- 这套纸色 + 印章朱红 + 宋体标题的语言是**完整且有辨识度**的，问题在没人用满，不在它不好；
- 换皮会让 App 与 Web 端品牌分叉。两端代码虽然刻意独立（见 `AGENTS.md` §4.1），但品牌不必跟着分叉；
- 改动因此集中在**布局、留白、信息层级、组件皮肤**，不碰品牌基因，回归风险小得多。

顺带把"单屏唯一强调色"这条原则真正执行了：`tokens.css:27` 自己写着
「强调色：单屏唯一，只给「关键动作」与「当前定位」」，
但原来的问答页上「退出」是朱红文字按钮，和「发送」抢同一个颜色。**把「退出」降为墨色次级文字**，
让朱红只留给登录与发送这两个真正的主动作。

## 4. 登录页：改了什么

| 改动 | 做法 |
| --- | --- |
| 露出纸面 | 删掉 `.panel` 的白底，叠一层与 App 外壳同款的朱红/赭金柔光渐变 |
| 品牌标识 | 新增 `src/components/BrandMark.vue`：内联 SVG 朱红方印 + 内层发丝键线 + 宋体「宝」（沿用 `favicon.svg` 的构成方式），配宋体字标「宝智审」与等宽小字副标题。三种布局 `seal` / `stacked` / `inline` |
| 图标 | 新增 `src/components/AppIcon.vue`：单 `name` 属性的内联 SVG 字形表（账号/密码/复制/对勾/发送/停止/回到底部/新建/退出）。工程里没有任何图标库（`@element-plus/icons-vue` 装了但从未引用），为九个图标引一整个库不划算 |
| 表单 | 48px 触控高度、内联图标、聚焦朱红描边、字号提到 16px |
| 演示账号区 | 两张卡片：点卡片本体填充表单（主操作），右侧按钮复制「账号 / 密码」（次操作，复制后变绿对勾 1.5 秒） |
| 可滚动 | 原来 `height:100dvh` + 垂直居中**且不滚动**，软键盘把视口压到 400px 上下时登录按钮会被裁掉 |

两个实现细节值得记：

1. **SVG 属性里不能用 `var()`。** `fill="var(--accent)"` 是无效的——CSS 自定义属性只在 CSS 声明里生效，
   presentation attribute 不接受。颜色必须写进 class 再由 CSS 给。
2. **卡片里不能嵌套按钮。** `button` 里再放 `button` 是非法 HTML，所以卡片拆成两个兄弟按钮：
   `.demo-fill`（`flex:1`，负责填充）与 `.demo-copy`（负责复制）。这样两个操作各自都有真实的按钮语义，
   `aria-label` 也能正常被无障碍树读到（后面验收时就靠它定位）。

## 5. 问答页：发现并修掉的四个真 bug

这一节的四个问题**都不是审美问题**，是原代码里的实际缺陷。视觉重做只是顺带。

### 5.1 `.prose` 没有覆盖标题样式，模型答案里一个 `##` 会撑出 25px 大标题

`src/styles/base.css:31-46` 把 `h1`~`h4` 定为宋体 **31/25/20/17px**——那是给整页文档定的层级。
而 ChatView 的 `.prose` 只覆盖了 `p/ul/ol/li/strong/a/blockquote/pre/code/table`，**唯独漏了标题**。
于是模型回答里出现 `## 说明` 时，会在聊天气泡里渲染出一个 25px 的宋体大标题，比正文大一倍。

修法：在 `.prose` 内把 `h1/h2` 收敛到 17px、`h3/h4` 到 15px，宋体保留。

> **教训**：组件库或全局样式表里的排版假设，是**按整页文档定的**。把它平移到"卡片内正文"这种
> 小尺度容器里，必须有意识地覆盖一遍。漏覆盖的往往不是常用标签，而是像标题这种"平时想不到会在气泡里出现"的标签。

### 5.2 每收到一个流式分片就无条件拽到底部

原实现：

```ts
async function scrollToBottom() {
  await nextTick()
  const el = listRef.value
  if (el) el.scrollTop = el.scrollHeight   // 无条件
}
```

调用点在**每个流式分片**里。后果是：回答生成到一半你想往上翻看前面的条款，会被一直拽回底部，
根本读不了。手机上这点尤其致命——屏幕小，长回答必然要翻。

修法：加"是否贴底"判定，只有在已贴底时才自动跟随，并在离开底部时浮出「回到底部」浮钮。

```ts
function onListScroll() {
  const el = listRef.value
  if (!el) return
  pinned.value = el.scrollHeight - el.scrollTop - el.clientHeight < 48
}

/** force 用于「发送」和「回到底部」；流式分片只在已贴底时跟随 */
async function followBottom(force = false) {
  if (!force && !pinned.value) return
  ...
}
```

### 5.3 输入框写死三行，placeholder 写着手机上不存在的按键

```html
<el-input type="textarea" :rows="3" placeholder="请输入你的问题，Ctrl+Enter 发送" />
```

两个问题：短问题也占三行高；而 **Android 软键盘没有 Ctrl 键**，那句提示在 App 里是死的，
发送实际上只能靠右边的按钮。

修法：换成原生 `textarea`，1 行起自动增高到 5 行（上限与 CSS 的 `max-height` 保持一致，
脚本里 `INPUT_MAX_HEIGHT = 140`），发送按钮做成 44px 圆形。placeholder 改成「输入你的问题…」，
`@keydown.ctrl.enter` 保留给接硬件键盘的场景。

顺带获得一个中文输入法的好处：`textarea` 里回车是换行，输入法用回车确认候选词不会误发送。

### 5.4 输入框字号 14px，低于 Android 不自动缩放的下限

`--fs-base` 是 14px，输入框直接继承。**Android Chrome 在聚焦字号小于 16px 的输入框时会自动放大页面**，
表现为点一下输入框整页变大。这不是审美偏好，是行为缺陷。

修法：登录页输入框与聊天输入框都显式设 `font-size: 16px`，并在两处都写了原因注释。

## 6. 演示账号：一次被实测推翻的推断

第 1 节的第 3 条诉求（要看到演示账号）撞上了一个安全设计。原实现用 `import.meta.env.DEV` 守着，
生产构建里整块不渲染——所以用户看到的截图里根本没有这块。要满足诉求就得换开关，而换开关的过程比预想的曲折。

### 6.1 我第一版的推断是错的

第一版我改成"默认开启"：`import.meta.env.VITE_SHOW_DEMO_ACCOUNTS !== 'false'`，
并在文档里断言"`VITE_*` 是运行时值，即使设成 `false`，凭据字符串仍会留在 bundle 里"。

**这个断言我没验证就写进了文档，而它是错的。** 实测：

```bash
cd frontend-app
VITE_SHOW_DEMO_ACCOUNTS=false npx vite build --mode android
grep -rl "Expert@2026" dist/assets/*.js     # → 没有任何命中
```

原因：`VITE_*` 和 `import.meta.env.DEV` 一样，**在构建期被静态替换成字面量**。
于是 `"false" !== 'false'` 被折叠成常量 `false`，`v-if` 的那个分支变成不可达，
只被该分支引用的 `DEMO_ACCOUNTS` 常量随之被 DCE 摘掉。
**"运行时开关"并不必然意味着凭据留在产物里**——取决于打包器能不能把分支折叠干净，而这在不同打包器、
不同代码结构下结论可能不同。这种事只能 grep 产物，不能推。

### 6.2 但实测同时暴露了一个真问题：默认开启是 fail-open

既然"凭据会不会随包出厂"完全由这个变量的取值决定，那"**变量没设**"这种最常见的情况就必须按最坏打算：

```ts
undefined !== 'false'   // → true，分支保留，凭据随包出厂
```

也就是说，谁在发版环境里忘了设这个变量，就会**静默**把凭据带出去。安全性性质上的默认值必须是
"安全的那一侧"，所以改成显式开启：

```ts
const showDemo = import.meta.env.VITE_SHOW_DEMO_ACCOUNTS === 'true'
```

未设、设成空串、设成别的值，一律不展示且凭据被 DCE。顺带还解决了原方案的一个痛点：
原来为了"演示包能看到"必须改代码（`DEV` 在 `--mode android` 下同样是 `false`），现在只需要环境变量。

### 6.3 三种场景的实测结果

| 构建 | 标志值 | bundle 里有 `Expert@2026` | 是否符合期望 |
| --- | --- | --- | --- |
| `--mode android`（模拟器/演示包） | `true`（来自 `.env.android`） | 有 | ✓ 演示包要能看到 |
| `--mode production`（发版） | 未设 | **没有** | ✓ 默认安全，且不需要任何额外操作 |
| `--mode android` 加环境变量覆盖 | `false` | 没有 | ✓ 显式关闭 |

> **终态仍不是这个。** 演示凭据不该编在前端：应当由后端按环境决定是否在登录接口返回演示账号信息，
> 前端只负责展示。这样"发版带不带凭据"由服务端一处控制，前端产物永远是干净的。
> 这次没做，是因为改动会跨到后端，超出"改 App 端两个页面"的范围。

## 7. 验收方法：在模拟器上做黑盒 GUI 验证

这一节是本次最耗时间、也最值得写的部分。具体命令已整理在
`docs/Android App 打包与运行说明.md` §7.6，这里只留方法层面的结论。

### 7.1 `uiautomator dump` 的 bounds 不能拿来点击

dump 用来**断言页面内容**非常好用：WebView 会把中文文本和 `aria-label` 都暴露成无障碍节点，
所以「普通用户」「复制专家用户账号密码」这类文本都能直接读到、`grep` 到。
我甚至靠它确认了给复制按钮写的 `aria-label` 是生效的。

**但它的坐标和帧缓冲不是同一个空间。** 同一个账号输入框：

| 来源 | 位置 |
| --- | --- |
| `uiautomator dump` 的 `bounds` | `[181,729][979,811]` |
| `screencap` 截图里实际位置 | `y 862..981` |

原点和比例都不同（两轴的缩放还不一致），**直接喂给 `input tap` 必然点错**。
我一开始就是信了 dump 的坐标，导致点到了完全别的地方。

> 顺带修正：`docs/Android App 打包与运行说明.md` 最早写的是"dump 的 bounds 比按坐标硬猜可靠"，
> 这次实测证明那句话是错的，已改。

### 7.2 从截图量坐标，别用 `sips`

macOS 自带的 `sips --cropOffset` 行为不可靠：`sips -c 120 1080 --cropOffset 2280 0` 本该裁出
底部 120px 的条带，实际**返回了整页**。这个坑很隐蔽——它不报错，只是默默给你错的东西，
于是你以为自己裁出来的是 A 区域，实际是 B 区域，后面所有坐标推导全错。

改用 PIL 裁剪，再用"沿某一列扫颜色、输出连续色带"的小脚本定位：

```python
from PIL import Image
Image.open("shot.png").crop((l, t, r, b)).save("crop.png")
```

之所以选颜色扫描，是因为**大色块比文字好定位得多**。登录页上唯一的大块朱红就是登录按钮，
一次扫描直接给出它在 `y 1326..1451`、中心 `(540,1388)`；同样方法也量出了两张演示卡片的精确范围
（`1663..1837` / `1863..2037`），这才让"点卡片填充"和"点右侧复制"两个不同的热区能被分别点到。

### 7.3 软键盘会重排布局，位移量很大

实测问答页输入区底边：键盘收起时 `y≈2296`，弹起时 `y≈1475`，**位移约 820px**
（≈313 CSS px，基本就是 Gboard 占掉的高度）。登录页的表现不同，它是整页滚动，
登录按钮从 `y 1326..1451` 上移到 `1174..1299`，只移了约 150px。

两个直接后果：
- 量坐标必须在**同一键盘状态**下做；
- `input keyevent 111`（ESC）**不一定能收起键盘**，得用 `keyevent 4`（BACK）。
  我没注意这点时，按"无键盘"算出的坐标落到了键盘按键上，往账号框里多打进了一个 `e`。

### 7.4 断言要基于**信号**，不要基于**时长**

判断"流式回答结束了没"，等固定秒数不可靠（这些回答在 5~8 秒之间完成，波动不小）。
可靠的信号是：**「依据来源」区块只在 `sources` 事件到达后才渲染**，所以看到它出现就等于流已结束。

这条在排查"停止生成"时救了场。第一次我点停止后没看到「（已停止生成）」标记，一度怀疑功能没做对；
用上面这个信号回查，才发现那一轮的完整回答已经渲染完了——**是我点晚了，不是功能坏了**。
把时序压缩到"提问后 1 秒"再点，标记正常出现。

## 8. 未复现的可疑现象

有一次 `pm clear` + `am start` 之后（**没有**先 `force-stop`），登录页正常显示，
我只发了**一次**点击（命中的是「普通用户」卡片的复制按钮），下一张截图却显示应用
**已登录为 `expert`**，且聊天页里已经发出了一条示例问题。

重复同样的单点操作**未复现**；加上 `am force-stop` 后全流程一次通过。
代码侧已排除：登录页没有任何隐式提交通路（表单 `@submit.prevent`，两张卡片的按钮都是
`type="button"` 且位于 `<el-form>` 之外，`el-button` 默认 `native-type` 是 `button`）；
两个输入框上的 `@keyup.enter` 是唯一入口，但前提是凭据已被填进去。

完整记录见 `docs/Android App 打包与运行说明.md` §7.8。写下来的价值在于"排除了什么"——
下一个遇到的人不用重走一遍。

> 排查时我还犯了一个错，值得单独记：我拿
> `grep -c api_jwt.py:147 /tmp/uvicorn-app.log` 当"登录次数"计数器，得出"发生了两次登录"的结论。
> **这是错的**——Python 的 `warnings` 默认对同一处告警只打印一次，计数恒为 1，跟实际登录次数无关；
> 而且那个 uvicorn 没开 access log，请求行根本不落盘。
> **不要把日志里的告警条数当事件计数器**；要数请求就自己加中间件或开 `--access-log`。

## 9. 可复用的经验清单

1. **"丑"要先拆成配色 / 布局 / 层级 / 品牌四类再定位**，别默认是配色问题。本例四类里三类有病，配色是好的。
2. **先查已有设计令牌有没有被用满，再考虑换皮。** 一套写了却没人用的令牌，比没有令牌更容易误导人。
3. **把"屏窄放不下…"、"只保留…"这类注释当成缺陷标记读。** 它们是删功能时留下的化石，说明那一段只被改到"能显示"，没被重新设计。
4. **全局排版是按整页文档定的**，平移到卡片、气泡这类小容器里必须逐标签覆盖一遍，尤其别漏标题。
5. **移动端输入框字号必须 ≥16px**，否则聚焦自动缩放。这是行为问题，不是审美偏好。
6. **安全性质必须实测，不能推断。** 我断言过一个并**不存在**的凭据泄露，同时又差点放过一个**真实存在**的 fail-open 默认值——两次都只要 `grep` 一下产物就能定论。凡是"产物里有没有敏感内容"这类问题，一律去查产物，不要推理打包器会怎么做。
7. **开关类配置的默认值要选"安全的那一侧"。** 本例取"显式开启"：变量没设时按最坏打算，而不是按最方便打算。
8. **给交互元素加 `aria-label` 有直接的自动化回报**——它会出现在无障碍树里，于是能被 dump 读到、被 `grep` 断言。
9. **验收要基于"只在成功路径上出现"的信号，不要基于等待时长。** 本例用的是「依据来源区块是否渲染」。
10. **平台 UI 的坐标不是稳定量**（键盘、滚动、动画都在改它）。要么每次都重新量，要么改用语义定位。
11. **不要用日志的告警条数当事件计数器**（`warnings` 会去重），也别在没开 access log 的服务上找请求记录。
12. **复现不了的现象要写下来，并写清排除了什么。** 只写"可能是模拟器问题"没有价值，写清"试过哪些、排除了哪些"才有。
13. **别信不报错的工具。** `sips --cropOffset` 给错结果时不报错；`uiautomator dump` 的坐标不对时也不报错。凡是用工具输出做推导，先用一个已知答案的样例校准一次。
