# 功能实现策略（RAG_demo 企业合规智能平台）

> 本文基于 `功能需求.md` 的 9 条需求与 `AGENTS.md` 的项目规范，结合现有骨架代码（backend/app、frontend/src）与参考项目（cosmetics-ai、Dify-Web）逐条分析实现方案。
> 目标是「如何落地」，而非需求罗列；涉及的具体方法/字段以当前代码为准，缺失项已标注。

---

## 0. 功能模块分类

先把 9 条需求按业务能力归类，后续实现按「模块」组织，而不是逐条平铺。

| 模块 | 涵盖需求 | 定位 | 状态 |
| --- | --- | --- | --- |
| 知识库管理 | ① 规章制度学习 + ⑨ 知识库维护 | 知识「进」与「管」，同一数据闭环 | ✅ 已确认合并 |
| 审查服务 | ② 合同审查 + ③ 规章制度审查 | 文本/文件输入 → 分块检索 + 多步推理审查 | ✅ 已确认合并 |
| 合规咨询 | ④ 合规性咨询 | 标准 RAG 多轮问答 | ✅ 已确认 |
| 内容纠错 | ⑤ 内容纠错 | 专家纠错 → 直接写入专家标注知识库（无审核） | ✅ 已确认 |
| 模板与合同生成 | ⑥ 合同模板库 + ⑦ 合同生成 | 模板入库 + docxtpl 填充 | 建议合并（待确认） |
| 文档生成 | ⑧ 规章制度生成 | AI 两段式（大纲→全文）+ 排版落盘 | 独立 |

## 1. 整体数据流与分层落地

每一条功能遵循同一套链路，差别只在「Dify 应用类型」和「是否涉及 Word/文件」：

```
前端 views/ ──axios/fetch──▶ 后端 api/（校验+鉴权）──▶ services/dify.py ──▶ Dify
                              │                            │
                              └── services/word_generator └── Dify 知识库(检索)
                              └── models + SQLite/PostgreSQL（元数据持久化）
```

关键共识（来自 AGENTS.md 与现有 `services/dify.py`）：

- **Dify 只做编排 + 知识库检索**，不把 Dify 当裸向量库自建检索链路。
- **每个业务场景一个 Dify 应用 + 独立 API Key**（`core/config.py` 预留 `DIFY_CHAT_APP_KEY` / `DIFY_REVIEW_APP_KEY` / `DIFY_GENERATE_APP_KEY`；合同审查与制度审查已拆为两个独立应用，`DIFY_REVIEW_APP_KEY` 后续需拆分为 `DIFY_CONTRACT_REVIEW_APP_KEY` / `DIFY_REGULATION_REVIEW_APP_KEY`）。
- 知识库分 **5 类**（法律法规 / 某钢现行规章制度 / 典型案例 / 审核规则 / 专家内容标注），对应 5 个 Dify dataset，按 `dataset_id` 隔离；前 4 类由知识库管理模块人工维护，专家标注知识库由纠错模块（⑤）自动写入。
- **角色模型**：普通用户（`user`）与专家（`expert`）两级；只有专家有内容纠错权限。

## 2. 模块一：知识库管理（需求① 规章制度学习 + 需求⑨ 知识库维护）

**本质**：一个完整闭环——「进」（① 上传→解析→入库 Dify）与「管」（⑨ 增删改查、持续更新），共用同一套 `Document` 模型和 `dify.py` 知识库方法集。

### 后端（`api/knowledge.py` + `services/dify.py` + `services/document_parser.py`）

**① 入库链路：**

1. 上传文件 → 存到 `UPLOAD_DIR`（`config.UPLOAD_DIR`），同时写一条 `Document` 记录（`status="uploaded"`）。
2. 调 `dify_client.upload_document()`（已封装，打 `POST /v1/datasets/upload-file`），拿到 `file_id`。
3. 再调「通过文件创建文档」接口 `POST /v1/datasets/{dataset_id}/document/create_by_file`（**当前 `dify.py` 缺此方法，需补**，现有只有 `create_by_text`），把 `file_id` + `dataset_id` + 分块策略写进知识库，回填 `Document.dify_document_id`，状态置 `parsing`。
4. 轮询 `GET /v1/datasets/{dataset_id}/documents/{id}/indexing-status`，索引完成后更新状态为 `ready`（需补异步任务/轮询机制）。
5. 复杂法务文档（扫描 PDF 等）在 `document_parser.py` 接 `unstructured`/`pymupdf` 先转纯文本，再走 `create_by_text`；普通文档走 Dify 内置解析（即 `document_parser.py` 当前的占位用途）。

**⑨ 维护链路（增删改查）：**

- 列表：`GET /knowledge/datasets`（调 `GET /v1/datasets`）、`GET /knowledge/documents?dataset_id=`（调 `GET /v1/datasets/{id}/documents`）。
- 删除：`DELETE /knowledge/documents/{dify_document_id}`（调 `DELETE /v1/datasets/{dataset_id}/documents/{document_id}`，**当前 `dify.py` 缺此方法，需补**）。
- 更新：文档内容更新（`update_by_text` 或删除重建）。
- 这些操作同步维护本地 `Document` 表，保证「本地元数据」和「Dify 文档」一致。

### 前端（`KnowledgeView.vue` + 统一上传组件）

- 上传组件处理进度/错误/重试，选「知识库类别」（法律法规/规章制度/典型案例/审核规则）→ 决定 `dataset_id`。
- 审核规则知识库以**文本添加**为主（`create_by_text`），也支持文件上传；其余三类以文件上传为主。
- 列表页展示 `Document` 状态流转（uploaded → parsing → ready → failed）。
- 知识库维护视图：四类业务知识库的文档树/列表 + 删除/重传/状态刷新。

### Dify 侧

- 4 类业务知识库 dataset（法律法规 / 规章制度 / 典型案例 / 审核规则），`indexing_technique="high_quality"`，embedding 模型在 `dify/` 说明文档里记录。
- 专家内容标注知识库由纠错模块（需求⑤）自动写入，见模块四。

### 关键点

- 把「文件落地存储」和「Dify 文档 ID」用 `Document` 表关联，这是「进」和「管」统一的基础。
- ① 是「进」，⑨ 是「管」，共用 `Document` 模型和 `dify.py` 知识库方法集，需在 `dify.py` 补齐一套完整的知识库 CRUD 封装（当前只有 upload 和 create_by_text，缺 `create_by_file`、`list_datasets`、`list_documents`、`delete_document`、`indexing_status`）。

## 3. 模块二：审查服务（需求② 合同审查 + 需求③ 规章制度审查）

**本质**：对「合同 / 新规章制度」做智能审查——识别违法违规风险条款，列明所违反的法律法规/规章制度名称、具体条款及链接，结合典型案例分析，并给出修改建议。②③ 同构，区别仅在**审查对象**与**比对的知识库范围**（② 比对法律法规+规章制度+典型案例；③ 只比对法律法规+现有规章制度）。

### 3.1 输入与编排

`POST /review` 按 `review_type` 创建任务：合同审查仅接收 PDF、DOC、DOCX、MD、TXT 文件；制度审查接收文本或上述文件。旧式 DOC 在上传前转换为 DOCX。合同文件上传 Dify 一次，Dify 文档提取器提取正文，Code 节点按段落切块，Iteration 对每块分别检索法规、制度与案例并生成结构化风险报告。制度审查继续由后端解析切块，逐块调用独立 Dify 应用。

### 3.2 合同审查结果与校验

合同工作流 End 返回 `chunks` 和等长的 `results`。每个结果携带该块原文、结构化报告和本次三路检索原始数据。后端按对应块校验风险原文、法规/制度引用、字段和风险等级，无法核对的风险标注人工复核；单块结果缺失或结构错误只计为该块失败。后端合并重复风险，生成 `summary` 并保存 `ReviewTask.result_json`。

### 3.3 任务接口与页面

提交后立即返回任务 ID，前端通过 `GET /review/{task_id}` 轮询。合同审查与制度审查分别有独立页面；两者复用任务和风险展示组件。合同文件在 Dify 工作流完成后统一回填块数与结果；制度审查仍在后端逐块更新进度。

当前合同 DSL 为 `dify/dsl/合同审查.yml`，文档提取器、Iteration 与后端校验已完成联调；制度 DSL 为 `dify/dsl/制度审查.yml`。

## 4. 模块三：合规性咨询（需求④，对话服务）

**本质**：标准 RAG 问答。差旅/接待/招采等事件，基于知识库做合规解读，支持多轮。

**后端（`api/chat.py`，已就绪）**

- `POST /chat`（阻塞）和 `POST /chat/stream`（SSE）都已实现，直接可用。
- 需补：`conversation_id` 用于多轮上下文（已透传）；把「咨询类别」（差旅/接待/招采）作为 `inputs` 传入，让 Dify 工作流在 Prompt 里切换语境。
- `sources` 已从 `metadata.retriever_resources` 提取（`ChatResponse.sources`），前端要展示引用。

**前端（`ChatView.vue`）**

- 用 `fetch + ReadableStream` 读 SSE（axios 不能流式），按 `\n\n` 切事件，逐 chunk 追加到消息气泡。
- markdown 渲染（markdown-it + highlight.js，已装依赖）。
- 渲染引用来源卡片。

**Dify 侧**：一个「合规咨询」Chatflow 应用，检索挂 **某钢规章制度库 + 专家知识库 2 库**，并在检索前加一个「多轮问题改写」节点（结合对话历史把追问补全为独立问题，改写异常时由 Code 节点回退原始提问）。DSL 见 `dify/dsl/合规咨询.yml`。

## 5. 模块四：内容纠错（需求⑤，专家纠错 + 专家标注知识库）

**本质**：区分普通用户与专家角色，**只有专家**可对大模型回答进行纠错；纠错内容**直接写入「专家内容标注」知识库**（无审核环节），模型下次回答时自动参考。

### 5.1 角色与权限

- **普通用户（user）**：提问、上传、审查、生成等正常使用，**无纠错权限**。
- **专家（expert）**：在普通用户基础上，额外拥有「内容纠错」权限。
- 登录时区分角色（`models/user.py` 的 `role` 字段改为 `user / expert`），JWT 携带角色，后端用 `require_expert` 依赖校验（替代原 `require_admin` 占位），前端按钮级权限控制纠错入口。

### 5.2 纠错流程（无审核）

1. 专家看到某条 AI 回答存在错误，点击「纠错」，提交改正后的内容（可附带原文、上下文、关联知识库）。
2. 后端**直接**把改正内容通过 `create_by_text` 写入「专家内容标注」知识库（Dify 新增的第 5 个 dataset），**无需管理员审核**。
3. 写入记录（含原回答 + 专家修正 + 关联信息）落库，供追溯。
4. 后续所有 RAG 应用（④咨询、②③审查）检索时挂上该知识库，模型下次回答即参考专家修正后的知识。

### 5.3 数据模型（简化）

- `models/feedback.py` 的 `CorrectionFeedback` **去掉审核状态**（不再需要 pending/approved/rejected），字段调整为：
  - `source_content`（原 AI 回答）、`corrected_content`（专家改正后内容）、`expert`（提交专家）、`dataset_id`、`document_id`、`chat_conversation_id`、`created_at`。
  - 保留一个 `write_status`（written/failed）表示「是否已成功写入知识库」，用于重试，而非审核状态。

### 5.4 后端（新增 `api/correction.py`）

- `POST /corrections`：专家提交纠错 → 校验 `require_expert` → 调用 `create_by_text` 写入专家标注知识库 → 落库 `CorrectionFeedback`。
- `GET /corrections`：查询纠错记录（专家本人/全部）。
- 写入失败时 `write_status=failed`，可重试。

### 5.5 前端（`CorrectView.vue`）

- 聊天界面对每条 AI 回复提供「纠错」按钮（**仅专家可见**，按钮级权限）。
- `CorrectView.vue` 展示纠错记录列表（**去掉审核工作台**），专家可查看自己的纠错历史。

### 5.6 关键点

- **权限模型**：user / expert 两级，`require_expert` 替代 `require_admin`，是纠错的唯一门槛。
- **无审核、直接回写**：专家纠错即时生效，闭环更短；「专家内容标注」知识库是沉淀专家知识、持续优化模型回答的核心载体。
- **知识库要挂到所有检索链路**：专家标注知识库必须接入 ④咨询、②③审查的检索节点，否则「下次回答参考」不成立。

## 6. 需求⑥ 合同模板库（模板库服务）

**本质**：多个合同类型的 `.docx` 模板文件导入、分类、管理。

**后端（`api/template.py` + `models/template.py`，骨架已有）**

- `ContractTemplate` 模型已有 `name`、`category`、`file_path`、`created_at`。
- 补全路由：
  1. `POST /templates`：上传 `.docx` 文件 → 存模板目录 → 写 `ContractTemplate`（`name`、`category` 合同类型）。
  2. `GET /templates`：列表（按 `category` 过滤、分页，用 `schemas/common.py` 的 `PageData`）。
  3. `GET /templates/{id}/download`：下载模板。
  4. `DELETE /templates/{id}`：删除。
- 模板文件单独一个 `templates/` 目录（区别于 `uploads/`）。

**前端（`TemplateView.vue`）**：模板列表 + 分类筛选 + 上传对话框。

**关键点**：模板是 `.docx` 且含 `{{ 变量 }}` 占位符（供 docxtpl 填充，见 ⑦）。导入时可做「变量占位符校验」，提示模板里有哪些变量。

## 7. 需求⑦ 合同生成（生成服务）

**本质**：选合同类型 → 基于模板 + 用户填的变量 → docxtpl 填充 → 生成 Word 初稿 → 预览 + 下载。

**后端（`api/generate.py` + `services/word_generator.py`）**

- `render_template(template_path, context, output_path)` 已实现（docxtpl），直接用。
- 补全流程：
  1. 前端选模板 + 填变量（`GenerateRequest.variables` 已有）。
  2. 后端按 `template_name` 找到 `ContractTemplate.file_path`，解析出模板占位变量列表（docxtpl 的 `get_undeclared_template_variables`）。
  3. `render_template()` 填充 → 生成到 `outputs/` 目录 → 返回文件 URL/ID。
  4. 预览：前端用 `docx-preview` 库，或后端转 PDF，或直接下载。
- **注意**：合同生成**不一定需要 Dify**，纯模板填充即可。只有当「生成合同条款正文」需要 AI 时，才先调 `DIFY_GENERATE_APP_KEY` 生成工作流产出内容，再塞进模板变量。需求 ⑦ 默认走**纯模板填充**，AI 作为可选增强。

**前端（`GenerateView.vue`）**：选合同类型 → 表单填变量 → 预览 → 下载。

**关键点**：区分「模板填充（确定性）」和「AI 生成（非确定性）」两条路径；⑦ 以模板填充为主。

## 8. 需求⑧ 规章制度生成（生成服务，两段式）

**本质**：用户提交「内容需求」→ **AI 生成大纲** → 用户检查修改大纲 → **AI 生成全文** → 落 Word → 预览下载。唯一「AI 生成 + Word 落盘」强耦合的功能。

**后端**

- 拆成两个接口（当前 `api/generate.py` 只有一个 `POST /generate`，需拆分）：
  1. `POST /generate/outline`：输入需求文本 → 调 `DIFY_GENERATE_APP_KEY` 工作流（`mode=outline`）→ 返回大纲（可编辑文本）。
  2. `POST /generate/document`：输入**用户确认后的大纲** → 调工作流（`mode=document`）→ 拿到 `sections_json` → 用 `python-docx` 程序化排版生成 `.docx` → **再自动做合规审查**（生成正文切块逐块调「制度审查」应用）→ 返回「文档 + 审查结果」；若不合规则带冲突清单与上一版全文重新生成，**最多自动修正 3 轮**（循环在后端，Dify 只做单轮生成）。
- 生成 + 多轮审查耗时较长，沿用审查服务的「任务 + 轮询」模式（`POST` 返回 `task_id`，`GET` 查进度与结果），前端展示「第 i 轮修正中 / 正在审查第 j/n 块」。
- 每轮的全文章节与审查结果落库（`ReviewTask.result_json` 或生成记录），供追溯与纠错。
- `services/word_generator.py` 需新增 `build_docx_from_sections(sections, output_path)`，用 `python-docx` 把章节结构渲染成标题/正文（当前只有 docxtpl 的 `render_template`）。
- 生成的规章制度可提示「是否入库」（回写知识库管理模块），形成闭环。

**前端（`GenerateView.vue` 分两个 Tab）**：

- Tab1 大纲生成：输入需求 → 展示大纲 → 可编辑 → 「确认大纲」。
- Tab2 文档生成：点生成 → 展示进度（第 i 轮修正 / 第 j 块审查）→ 预览文档 → **同时展示自动合规审查结果**（冲突清单 + 修改建议）→ 下载。

**Dify 侧**：「规章制度生成」工作流，`inputs` 传 `requirement` / `mode` / `outline`，修正轮次另传 `previous_sections` / `review_conflicts` / `revision_round`；生成阶段挂「法规 + 现行制度」2 库作写作参照。审查不重复实现，复用「制度审查」应用。DSL 见 `dify/dsl/规章制度生成.yml`。

**关键点**：大纲是**用户确认的中转态**，前后端都要把它当作一等数据传递，不能一次性 AI 直出全文。自动修正必须**基于上一版全文**改（只给冲突清单会让模型整篇重写，可能引入新冲突而循环不收敛），且回传前冲突清单要先合并去重、按等级排序并截断条数。

## 9. 跨功能基础设施（需先补齐）

这几项是所有功能的前置，目前是占位：

1. **RBAC 权限落地**（需求 ⑤ 依赖）：角色区分 `user / expert`，`deps.py` 里把 `require_admin` 占位改为 `require_expert` 真实校验 `User.role`；登录 `api/auth.py` 目前不验密码，需接 `passlib`/`bcrypt` 哈希校验 + 种子专家账号。
2. **`dify.py` 知识库方法补全**：缺 `create_by_file`、`list_datasets`、`list_documents`、`delete_document`、`indexing_status`，是知识库管理模块的直接依赖。
3. **文件解析落地**：`document_parser.py` 需真正实现 PDF（`pymupdf`）与 docx（`python-docx`）解析，是审查服务「文件输入」的前置。
4. **异步任务与进度**：审查服务的长文档分块处理需要 `BackgroundTasks`（MVP）/ Celery（生产）+ `ReviewTask` 进度模型。
5. **文件存储规范**：`uploads/`（知识库文档 + 待审查文件）、`templates/`（合同模板）、`outputs/`（生成的 Word）三个目录分开，本地文件系统起步，生产换对象存储。
6. **Word 生成补 `python-docx` 程序化排版**：现有只有 docxtpl，需求 ⑧ 需要「无模板排版」能力。
7. **异步索引轮询**：文档上传后 Dify 是异步索引，需要轻量轮询/任务机制更新 `Document.status`（MVP 用前台轮询即可）。
