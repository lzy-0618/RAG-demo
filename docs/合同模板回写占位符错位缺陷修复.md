# 合同模板回写占位符错位缺陷修复

> 发现日期：2026-09-14　|　场景：合同模板结构化 —— 把 AI 识别出的字段回写成 `{{ 占位符 }}`
> 结论一句话：**AI 只输出 `anchor`，回写逻辑只认 `candidate_id`，两者契约不对齐导致回写退化成"在段末追加占位符"，原填空痕迹（下划线）没被替换——而变量集合自检照样通过。**
> 相关设计：`docs/合同模板导入与合同生成实现思路.md` 第 2.3 节

---

## 1. 现象：产物"看起来成功"，内容却是错的

模板里这一段是纯下划线填空（**不含任何 `{{ }}`**，这正是"不让用户手写变量"要解决的场景）：

```
甲方（采购方）：__________
第一条 采购标的：__________________
```

走完"扫描 → AI 识别 → 回写 → 自检"，接口返回 `code: 0`、`status: review`，字段清单也对（5 个字段、中文标签、类型、必填都合理）。但生成的标准化模板长这样：

```
甲方（采购方）：__________{{ party_a_name }}
第一条 采购标的：__________________{{ procurement_subject }}
```

**下划线还在，占位符被追加到了填空后面。** 用户填完值生成合同时，会得到"甲方（采购方）：__________某钢股份有限公司"这种东西——填空线跟着合同一起打印出去。

对照一下正确产物：

```
甲方（采购方）：{{ party_a_name }}
第一条 采购标的：{{ procurement_subject }}
```

`标签：` 后面为空的那些位置（`合同编号：`、`签约地点：`）反而是对的，因为"追加到段末"在那里恰好等于"插入到标签后面"。**只有下划线填空这类"填空字符要被替换掉"的位置才会暴露问题**，所以第一眼很容易漏掉。

---

## 2. 为什么自检没拦住

当时的自检是这条断言（见设计文档 2.3 节）：

```
set(标准化模板解析出的变量名) == set(确认的字段集合)
```

出问题的文档里，占位符**确实写进去了**——只是写错了位置。变量集合完全一致，断言通过。

这是这次踩坑最值得记的地方：**自检断言的维度选窄了。** "变量集合正确"只覆盖了"有没有"，没覆盖"在对不对的地方"和"原来的填空有没有被清掉"。回写这一步的正确性其实有三维：

| 维度 | 原来的自检 | 后果 |
| --- | --- | --- |
| 占位符**存在**（变量集合） | ✅ 有断言 | — |
| 占位符**位于正确位置** | ❌ 无断言 | 追加到段末也算通过 |
| 原填空痕迹**已被替换** | ❌ 无断言 | 下划线残留也算通过 |

另外，写入方式 `write_modes` 当时已经全部是 `append_run`（不是 `replace`/`insert`），这个信号就摆在返回值里，但没人看——**它其实是"回写没有命中填空位置"的直接证据**。

---

## 3. 根因：两端的接口契约不对齐

- **Dify 应用六的提示词**只要求模型输出 `anchor`（文档锚点，如 `p2`），**没有要求输出 `candidate_id`**（扫描阶段给每个候选空位分配的编号，如 `c1`）。
- **后端回写逻辑**（`template_rewrite._apply_one`）只按 `candidate_id` 找落点：

```python
candidate = scan.find_candidate(field.get("candidate_id") or "")
if candidate is not None:
    ...  # 精确替换填空跨度
# 找不到就退化成：在 anchor 所在段落的末尾追加占位符
paragraph.add_run(placeholder)
```

`candidate_id` 恒为空 → 永远走不到精确替换分支 → 全部退化追加。

**根因不在"模型输出得不对"，而在"降级路径太安静"。** 拿不到落点时，代码默默换了一种语义完全不同的写入方式（"替换这段填空" → "在这段末尾追加"），既没有报错也没有告警。契约不对齐本该是显式失败，而不是静默降级。

---

## 4. 修复

两处改动，分别在 `template_rewrite.py` 的写入侧与自检侧。**不动 Dify 应用**，因此不需要重新导入、不换 API Key。

### 4.1 写入侧：按锚点回退解析候选

`candidate_id` 是"精确指定"，`anchor` 是"段落级线索"，两者都能定位。让回退路径先尝试用 `anchor` 把落点找回来：

```python
def _resolve_candidate(scan, field, used: set[str]) -> dict | None:
    """定位字段对应的候选空位。

    优先用 AI 给出的 candidate_id；缺失时按 anchor 回退解析——应用六的提示词只要求
    输出 anchor，若只认 candidate_id 会退化成"在段末追加占位符"，导致填空题变成
    甲方（采购方）：__________{{ party_a_name }}（原填空没被替换掉，实测踩过）。
    """
    candidate = scan.find_candidate(field.get("candidate_id") or "")
    if candidate is not None:
        return candidate

    anchor = field.get("anchor") or ""
    siblings = [c for c in scan.candidates
                if c["anchor"] == anchor and c["id"] not in used]
    if not siblings:
        return None
    if len(siblings) == 1:
        return siblings[0]

    # 同一段落有多个填空：先按标签文字匹配，否则取最后一项
    # （"标签：____" 形态下填空在标签之后）
    label = (field.get("label") or "").strip()
    if label:
        for item in siblings:
            if label in item["context"]:
                return item
    return siblings[-1]
```

三个设计要点：

1. **用 `used` 集合防踩踏**：同一段落若有多个填空，两个字段可能解析到同一个候选，导致一个占位符覆盖另一个。已被占用的候选不再参与解析。
2. **先按标签文字匹配**：字段的中文标签（如"甲方名称"）常常就出现在候选的上下文里（`甲方（采购方）：__________`），这是最强的消歧信号。
3. **否则取最后一个候选**：典型的"标签：____"排版中，填空位于标签之后，取段内最后一个候选最贴近语义。这是启发式，不是精确解；段落里有两个以上填空时仍可能选错，需要人工在复核页确认（复核页本来就是要人工过一遍的）。

### 4.2 自检侧：补上"残留检查"

把上面缺的两个维度补成断言——写入后，该段落里必须出现占位符，且不能再残留原填空字符：

```python
def _verify_residuals(scan, applied) -> list[str]:
    """自检补齐：占位符确实写进去了，且原有的填空痕迹没有残留。

    只比对变量集合会漏掉"占位符追加在下划线后面"这类文档——变量齐了但填空没被替换。
    """
    problems = []
    for field, outcome in applied:
        candidate = outcome.get("candidate")
        anchor = field.get("anchor") or (candidate or {}).get("anchor") or ""
        paragraph = scan.paragraph(anchor)
        if paragraph is None:
            continue
        text = paragraph.text
        if f"{{{{ {field['key']} }}}}" not in text:
            problems.append(f"{field['label']}：占位符未写入对应段落")
            continue
        # blank 候选的原文就是填空字符（下划线/空白）；
        # label_empty 的原文是标签本身，本应保留，故不检查
        if candidate and candidate["kind"] == template_scan._KIND_BLANK and candidate["text"]:
            if candidate["text"] in text:
                problems.append(f"{field['label']}：原填空痕迹仍残留在文档中")
    return problems
```

调用点在保存文件**之前**，自检不过就不产出可用产物：

```python
residuals = _verify_residuals(scan, applied)
if residuals:
    raise BizError(message="标准化模板自检未通过：" + "；".join(residuals))
```

注意 `label_empty`（`合同编号：` 这类）的候选原文是**标签**，标签本来就该留在文档里，所以只对 `blank` 类候选做残留检查——否则会误报。

### 4.3 修复效果

同一份模板重跑，写入方式从清一色 `append_run` 变成正确的组合：

```
修复前：{'contract_no': 'append_run', 'party_a_name': 'append_run',
         'party_b_name': 'append_run', 'sign_location': 'append_run',
         'procurement_subject': 'append_run'}

修复后：{'contract_no': 'insert', 'party_a_name': 'replace', 'party_b_name': 'replace',
         'sign_location': 'insert', 'procurement_subject': 'replace'}
```

标准化模板：

```
合同编号：{{ contract_no }}
甲方（采购方）：{{ party_a_name }}
乙方（供应方）：{{ party_b_name }}
签约地点：{{ sign_location }}
第一条 采购标的：{{ procurement_subject }}
```

## 5. 回归测试

在 `backend/scripts/smoke_structure.py` 增加了第 6 步，**专门覆盖"只给 anchor、不给 candidate_id"这个形态**（也就是应用六的实际输出形态）：

```python
print("\n6) 回归：只给 anchor、不给 candidate_id（应用六的实际输出形态）")
result = template_rewrite.rewrite_document(
    fixture,
    [{"key": "party_a_name", "label": "甲方名称", "required": True,
      "candidate_id": "", "anchor": pick(scan.candidates, "blank", 0)["anchor"]},
     ...],
    anchor_only,
)
check("按锚点回退可定位到填空处", result["write_modes"]["party_a_name"] == "replace")
check("下划线痕迹已清除（占位符未追加在下划线之后）",
      any(t.strip() == "甲方（采购方）：{{ party_a_name }}" for t in texts))
```

断言直接盯住**产物的最终文本形态**，而不是中间状态——这样即使以后回退逻辑再改，只要产物错了就会被抓住。

复现命令：

```bash
cd backend && .venv/bin/python scripts/smoke_structure.py
```

## 6. 可复用的经验清单

1. **接口两端都要各自验证"对方会给我什么"**。这里 DSL 提示词与后端解析逻辑分属两人（/两个阶段）产出，契约靠约定而非编译期检查，一旦不一致就是静默降级。凡是跨边界（跨进程、跨 AI 与代码）的数据契约，落地后都要**用真实产物对一遍**，不能只看单测。
2. **降级路径必须显式**。拿不到精确定位时改走"近似写入"，这类降级要么报错、要么至少把降级原因回传（这里的 `write_modes` 字段就是那个信号，应该在有 `append_run` 时给出警告而不是静默接受）。
3. **自检要按"正确性的维度"设计，不能只挑好写的那个维度**。这次只断言了"变量存在"，漏掉了"位置对"和"原痕迹被替换"。设计自检时先问：这个步骤可能以哪几种方式错？每种都该有断言。
4. **断言产物的最终形态，而不是中间数据结构**。变量集合、写入方式都是中间态；用户看到的 `.docx` 文本才是事实。
5. **AI 输出的"格式对"不等于"语义对"**。字段清单本身完全合理（键、标签、类型、必填都对），错的是它和后端约定的定位字段不匹配。看 AI 输出质量时要连带检查它的**下游能不能消费**。
6. **回退解析是启发式，要留人工确认口**。同段多填空时"取最后一个"并不保证正确，所以整套流程保留了复核页——识别结果永远不直接生效。

## 7. 后续演进（2026-09-18）：从"锚点启发式"到"槽位精确绑定"

本文记录的锚点回退解析（第 4.1 节）当时是**唯一**的定位手段，现在退居为**最后一道兜底**。触发这次演进的是另一份真实模板（免烘烤捣打料合同，`data/hetong/2026-9-11 …doc`），它暴露出三类新痕迹，也说明"按 anchor 猜落点"这条路走到头了。

### 7.1 新增两类候选

| 类型 | 形态 | 关键点 |
| --- | --- | --- |
| `form_field` | `甲方：PUR_BILL_TO_NAME` —— Word 表单域（`fldChar` + `instrText FORMTEXT`），**域结果文本就是变量名** | 一个域一条候选，`start/end` 精确到域结果文本 |
| `hash` | `致#供应商名称#：` —— 井号包裹的占位符 | 区间覆盖两个 `#`，内文常是中文 |

顺带修掉两个扫描缺陷：合并单元格被 `row.cells` 重复返回（同一空位出了 4 个候选）、浮动文本框里的域在外层段落上表现为"空段落"（AI 看不到，回写还会把整个文本框删掉）。

### 7.2 落点定位从"猜"变成"绑"

同名变量（一个变量多处出现、文本框 Choice/Fallback 两份副本）在扫描阶段就按 `name` 聚成**槽位**，AI 返回 `slot_id`，回写按槽位取出全部候选逐个写。于是：

- **不再需要"先按标签文字匹配、否则取最后一个候选"**——这是本文第 4.1 节的启发式，现在只在拿不到 `slot_id` 也没有 `name` 时才用；
- **同段多变量不再互相踩**：实测一份合同里通知条款 8 个变量、生效期限 9 个变量挤在一个段落，靠精确区间 + 从后往前写即可各自落位；
- **一个变量一处填写、多处生效**：`PUR_BILL_TO_NAME` 在首部与签署信息表各一处，只生成一个字段、写两个占位符。

### 7.3 自检再加两个维度

本文第 4.2 节补的"残留检查"仍不够——它挡不住**整段被替换**（变量齐了，但 `甲方：` 和条款正文都没了）。现在共四类断言（见 `docs/合同模板导入与合同生成实现思路.md` 2.3 节），其中两条是这次新加的：

```python
# ① 跨度之外的文字逐字未变：把"只替换该替换的"变成可断言的等式
if paragraph.text != _expected_text(original, writes):
    problems.append(f"{anchor}：字段跨度之外的文字被改动了")

# ② 同一段落同一个键只出现一次：防落点重复把占位符写坏
for (anchor, field_key), count in intended.items():
    if paragraph.text.count(f"{{{{ {field_key} }}}}") != count:
        problems.append(f"{field_key}：占位符出现次数与预期不符")
```

第 ② 条不是杞人忧天：修 `slot_id` 绑定时真的踩到过——字段同时带 `candidate_ids=["c0"]` 与 `candidate_id="c0"`，解析函数把**同一个候选取了两遍**，对同一段落写两次，产出 `甲方：{{ x }}{{ x }}` 这种坏占位符。而"包含占位符"和"预期文本"两种检查都放它过去了（后者与回写用的是同一套替换算法，两边一起错）。**自检不能只用与实现同源的算法**——第 ② 条之所以有效，正因为它换了一个独立维度（计数）来验。

### 7.4 新增回归

`backend/scripts/smoke_structure.py` 增加第 8~10 步，覆盖表单域 / `#...#` / 文本框 / 同段多变量 / 同名多落点 / 标签消歧；`backend/scripts/smoke_form_field_doc.py` 用上面那份真实 `.doc` 跑端到端（文件不存在时跳过）。
