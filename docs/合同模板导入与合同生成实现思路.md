**AI 识别链路已联调通过**（2026-09-14）：应用六导入 Dify 后，对一份**纯下划线填空**的合同模板（不含任何 `{{ }}`）实测——2 秒返回，识别出 5 个字段（`contract_no` / `party_a_name` / `party_b_name` / `sign_location` / `procurement_subject`），中文标签、控件类型（`采购标的` 正确判为 `textarea`）、必填标记、置信度与判断理由均合理，并正确忽略了文档标题与固定条款。随后"复核确认 → 必填拦截 → 生成 → 产物内容校验"全部通过，生成的合同里填空位置被正确替换、无残留。

联调中发现并修复的一个真实缺陷（已加回归测试）：应用六的提示词只要求输出 `anchor`，而回写逻辑原先只认 `candidate_id`，结果退化成"在段末追加占位符"，产出了 `甲方（采购方）：__________{{ party_a_name }}` —— 变量集合自检照样通过，因为占位符确实存在，只是原本的填空没被替换。修法两条：① 回写时**按锚点回退解析候选**（同一段落多个候选时先按标签文字匹配、否则取最后一项，并用 `used` 集合防止两个字段落在同一处）；② 自检增加**残留检查**：写入后该段落里不能再留原填空字符，否则视为失败。

## 0. 现状基线与问题

当前实现（本轮改动前的状态）是一条纯确定性的"占位符填充"链路：

| 环节 | 现状 | 关键代码 |
| --- | --- | --- |
| 模板导入 | 只收 `.docx`；用 docxtpl `get_undeclared_template_variables()` 解析出文档中**已存在**的 `{{ 变量 }}`，缓存进 `variables_json` | `backend/app/services/template.py:create_template`、`backend/app/services/word_generator.py:extract_template_variables` |
| 模板管理 | 列表（分页 + 自由文本分类过滤）、下载原文件、删除（连文件物理删除）；`PATCH` 改元信息但前端无入口 | `backend/app/api/template.py`、`frontend/src/views/TemplateView.vue` |
| 合同生成 | 进页面拉最多 100 个模板塞进一个平铺下拉 → 把变量名铺成一片 `el-input` → docxtpl `render()` 填充 → 下载 Word | `frontend/src/views/ContractGenerateView.vue`、`backend/app/api/generate.py:generate_contract` |
| 生成产物 | 只写 `outputs/` 文件，不落库 | `backend/app/services/template.py:render_contract` |

对照 `功能需求.md` 的原文——「可根据**合同类型**，基于模板库中的合同模板自动生成合同初稿，提供**预览**和**下载**功能」——存在四个硬缺口：

1. **预览完全没有实现**：全局搜 `预览` / `preview` 零命中，生成后只有一条 alert 和一个下载按钮。
2. **没有"按合同类型"的路径**：只有一个平铺模板下拉，分类仅拼在选项文字后的括号里；且硬编码 `page_size: 100`，超过 100 个模板在界面上选不到。
3. **变量由用户手工定义**：变量名、数量、语义 100% 取决于写模板的人在 Word 里敲了什么。程序只知道"有个变量叫 `party_a`"，不知道它是"甲方名称"。结果是填报表单的 label 就是裸变量名，没有中文标签、没有控件类型、没有必填校验，变量没填一律补空串，**能生成出一份关键信息全空的合同并提示成功**。
4. **生成是一次性动作**：不落库、无历史、无法追溯；产物下载接口 `GET /generate/files/{file_name}` 任何登录用户凭文件名即可下载他人产物；文件名用秒级时间戳（`word_generator.safe_filename`），同模板同秒生成会互相覆盖。

此外，模板的导入/删除目前只校验登录（`api/template.py` 全用 `get_current_user`），普通用户即可删除模板库内容，而更该受控的这个环节反而比纠错模块宽松（纠错已用 `require_expert`）。

## 1. 设计原则

"变量不该由用户手写"这个判断是成立的：在 Word 里敲 `{{ 甲方 }}` 是让业务人员承担程序员的工作，而且他敲出来的变量名程序也读不懂语义。但要落地"程序智能识别"，必须先划清边界，否则会滑向"让大模型直接写合同"——那是另一个极端，合同场景承受不起（不可复现、不可复核）。

| # | 原则 | 理由 |
| --- | --- | --- |
| 1 | **AI 只在导入阶段用一次，生成阶段保持 100% 确定性** | 智能集中在"把一份普通 Word 合同变成结构化模板"；结构定下来后，每次生成仍是 docxtpl 确定性填充，同样输入永远同样输出 |
| 2 | **AI 只输出"字段清单"，不产出文档内容，也不碰文件** | 模型产物是一段 JSON（有哪些字段、叫什么、什么类型），写回文档是程序的事。AI 出错的最坏后果是"字段列错了"，而非"合同内容错了" |
| 3 | **识别结果不直接生效，必须人工复核** | AI 识别必然有错，合同出错代价高。复核页同时解决"表单是裸变量名"与"模板改不了"两个问题 |
| 4 | **回写后程序自检** | 写完立刻用 docxtpl 重新解析标准化模板，断言"解析出的变量集合 == 复核确认的字段集合"。把"AI 是否可信"从主观判断变成可程序化验证的断言；失败则不覆盖原文件 |

## 2. 合同模板导入：从「解析占位符」升级为「文档结构化」

原来是"读一下有没有 `{{ }}`"，新设计是**三道工序 + 一道复核**。

```
上传 .docx
  → 工序1 确定性扫描（程序）      ：产出「候选空位清单」+ 文档结构大纲
  → 工序2 语义理解（Dify 应用六） ：产出「字段清单 JSON」
  → 工序3 回写与自检（程序）      ：产出「标准化模板」，并断言字段集合一致
  → 工序4 人工复核（前端）        ：确认后才启用，进入生成页可选
```

### 2.1 工序 1：确定性扫描（程序，不依赖 AI）

先把 `.docx` 拆成**可定位的文本单元**，再穷举出所有"看起来要填的位置"。关键认知：一份合同里"待填"的痕迹有七种，程序能穷举，只是不知道它们的语义。

| 候选类型 | 识别方式 | 例子 | 可靠性 |
| --- | --- | --- | --- |
| `form_field` Word 表单域 | `w:fldChar`（begin/separate/end）+ `w:instrText` 含 `FORMTEXT`，**一个域一条候选，区间精确到域结果文本** | `甲方：PUR_BILL_TO_NAME` | 最高：作者已显式标记，且结果文本就是变量名 |
| `hash` `#...#` 占位符 | 正则 `#([^#\n]{1,40})#`，区间覆盖整段井号 | `致#供应商名称#：` | 高：作者显式标记 |
| `sdt` Word 内容控件 | XML 中的 `w:sdt`（段落本身有可见文字时才整段出候选） | 作者用「开发工具」插入的控件 | 最高 |
| `jinja` 已有 Jinja 占位符 | docxtpl `get_undeclared_template_variables()`；被 Word 拆散到多个 run 的用 `patch_xml` 复原 | `{{ party_a }}` | 高 |
| `blank` 下划线 / 空白填空 | 段落文本中连续 `_{2,}`、全角空格 `　{2,}`、连续半角空格 ` {3,}`；**与具名占位符重叠或紧邻的空白不算** | `甲方：__________` | 中：需上下文判断 |
| `label_empty` 标签后为空 | 段落匹配 `^(.*?)[:：]\s*$` | `合同金额：` | 中 |
| `empty_cell` 表格空单元格 | 单元格文本为空且所在列有表头 | 表格中的金额格 | 中 |

**输出不是"变量列表"，而是「候选清单」**，每条包含：

| 字段 | 含义 |
| --- | --- |
| `anchor` | 定位信息（`pN` 全局段落号，含表格单元格与浮动文本框内的段落）——工序 3 回写靠它精确落点 |
| `kind` | 上表七类中的哪一类 |
| `name` | 具名候选的原名：`form_field` 是域结果文本（`PUR_BILL_TO_NAME`），`hash` 是井号内文（`供应商名称`）；其余为空 |
| `start` / `end` | 在所在段落文本中的字符范围，回写按它精确替换，**不再整段替换** |
| `context` | 所在段落全文 + 前后段落 + 所在表格表头（供工序 2 判断语义） |
| `label_hint` / `owner_hint` | 变量左侧的标签文字与主体（甲方/乙方），给 AI 做提示 |

同时产出一份**文档结构大纲** `doc_outline`：把段落与表格按顺序展开成带编号的纯文本，供工序 2 通读全文。

#### 槽位（slot）：同名变量合并

`form_field` / `hash` 带 `name`，**同名即同一个变量**。扫描完成后按 `name` 聚成「槽位」（`group_slots`），一个槽位一个待填变量：

```
{slot_id, name, kind, anchors: [...], candidate_ids: [...], contexts: [...],
 header, label_hint, owner_hint}
```

这么做解决三件事：

1. **同名变量只识别一次**：`PUR_BILL_TO_NAME` 在首部与签署信息表各出现一次，是一个字段、多处落点，填一次两处生效——若按候选逐条交给 AI，会产出两个字段、逼用户填两遍。
2. **AI 不必自己去重**：判断单位从 41 处出现收敛成 37 个槽位，重键问题在结构上消失（`normalize_fields` 里的重键兜底只剩防御意义）。
3. **文本框两份副本都能写上**：浮动文本框存在 `mc:AlternateContent` 里，`mc:Choice`（wps 形状）与 `mc:Fallback`（VML 形状）各存一份内容相同的副本。Word/WPS 读 Choice，LibreOffice（PDF 预览链路）读 Fallback，两份都要回写，否则另一处会显示旧文本。扫描时两份都收进同一个槽位，正好。

#### 中文标签重名要能区分

甲乙双方成对出现的字段在原文里标签一模一样（`单位名称`、`联系地址`、`开户银行`、`账号`、`社会信用代码`，实测一份模板 7 组），直接展示会让填表人分不清哪个是甲方哪个是乙方。处理：

- key 天然不重（`BANK_NAME` vs `SUPPLIER_BANK_NAME`），**不合并语义相同的字段**——是否真的是同一个业务值由人工在复核页决定；
- `owner`（甲方/乙方/附件）由 AI 判断、后端只做提示与兜底：列头写了「甲方（签章）/乙方（签章）」这类结构信号最可靠，正文里靠变量左侧的甲乙方推断（会误判的只发生在同时提到双方的条款里，而那些字段标签本来就不重名）；
- 后端 `_disambiguate_labels` 保证**标签全局唯一**：重名即加主体前缀（甲方联系地址 / 乙方联系地址），主体也分不开时补序号并出警告。

#### 其它两个坑（都实测踩过）

- **合并单元格必须按元素去重**：`row.cells` 会把横向合并的单元格按跨列数重复返回，一个物理段落被编成多个锚点，同一个空位在候选清单里出现多次（实测 `TAX_RATE` 出了 4 个重复候选）。改为直接遍历 `w:tr` 的子 `w:tc`，列号按 `w:gridSpan` 累加。
- **浮动文本框里的段落要单独收**：`Paragraph.text` 只读 `w:p` 的直接 `w:r` 子节点，取不到绘图里的文字，所以文本框里的域在外层段落上表现为"空段落"——既不进大纲（AI 完全看不到合同编号、签订日期），回写时还会因为给绘图 run 赋 `.text` 而**把整个文本框删掉**。现在下钻 `w:txbxContent`，把内层段落编成独立单元（`mc:Fallback` 副本标 `shadow`：不进大纲，但照常出候选、照常回写）。

> 这一步能把形如 `甲方（采购方）：某钢股份有限公司` 的段落正确切成"标签 + 值"两部分，值部分是"已有值"而不是待填项。

### 2.2 工序 2：语义理解（Dify 新增应用六「合同模板结构化」Agent）

**输入**：`doc_outline`（带编号的文档结构文本）、`candidates_json`（工序 1 的候选清单）、`slots_json`（工序 1 的槽位清单，**模型的实际判断单位**）、`template_name`。

**编排形态（已确认：由 Agent 承担识别）**：采用**「Workflow 内含 Agent 节点」**的形态，即外层仍是 Workflow 应用（`inputs → outputs` 契约不变，后端继续复用既有的 `run_workflow`，无需新增调用方式），内层放一个 Agent 节点，由它自行决定如何通读文档、如何把候选空位归并成字段。

链路：`Start(doc_outline, candidates_json, slots_json, template_name) → Agent（识别待填字段）→ Code（JSON 规整与字段校验）→ End(fields_json, parse_error)`。

**给模型的硬规则**（`slots_json` 带来的）：

- **一个槽位一个字段**，`slot_id` 原样照抄。判断单位是槽位而不是"大纲的行"——一个段落里可能有 8~9 个变量，按行数会数错。
- **带 `name` 的槽位，`key` 必须原样沿用 `name`**：`PUR_BILL_TO_NAME`、`DTK9980` 这类名字来自甲方既有模板体系，改写会让生成的合同对不上他们的数据字段。只有 `#...#` 的内文是中文时才另起英文 key，中文原名进 `label`。
- `label` 必须**全局唯一**且带主体（「甲方联系地址」而不是「联系地址」）；`owner` 取甲方/乙方/附件，后端的 `owner_hint` 只是提示（同时提到双方的条款里容易误判），以模型判断为准。
- 类型按语义推断：日期类 → `date`，金额/天数/份数/税率 → `number`，「第__种方式」→ `select`。

> 导入时需在 Dify 控制台确认 1.17 的 Agent 节点可用（含 `agent_strategy` 与工具配置）。若该版本不可用，退化为 `agent-chat` 应用，把输出契约写进提示词，后端改走 `chat()`——这是形态降级，不影响工序 1/3/4。

**输出** `fields_json`：

```json
{
  "contract_type": "采购",
  "fields": [
    {
      "key": "PUR_BILL_TO_NAME",
      "label": "甲方单位名称",
      "type": "text",
      "required": true,
      "slot_id": "s2",
      "owner": "甲方",
      "source_name": "PUR_BILL_TO_NAME",
      "anchor": "p3",
      "default": "",
      "options": [],
      "confidence": 0.96,
      "reason": "模板表单域名为 PUR_BILL_TO_NAME，位于『甲方：』之后"
    }
  ],
  "ignored": [
    { "slot_id": "s30", "anchor": "", "reason": "已有固定条款正文，无需填写" }
  ],
  "notes": "识别到 37 个待填字段"
}
```

> `slot_id` 是回写的枢纽：后端凭它取回该变量的全部落点（含文本框两份副本）逐个写占位符。旧版应用不返回 `slot_id` 时，后端用 `source_name` / `key` 反查槽位，仍能合并同名变量；再不行才退回按 `anchor` 的启发式定位（见 `docs/合同模板回写占位符错位缺陷修复.md`）。

**Agent 负责四件事**：

1. 判断每个槽位是否真的待填——排除已有值（`签订地点：北京市`）、排除固定条款正文；
2. 沿用模板原名做 `key`（具名槽位），给出唯一的中文 `label` 与 `owner`；
3. 定 `type`（`text` / `textarea` / `date` / `number` / `select`）与 `required`；
4. 识别 `contract_type`，并补上程序漏掉的（如整段"（此处填写付款方式）"）。

**Agent 输出不稳定性是这条路线的主要风险**，用四道措施收敛：

1. **强约束输出**：Agent 节点开 `structured_output`，把 `fields_json` 的 JSON Schema 作为契约，不接受自由文本；
2. **Code 节点兜底**：沿用 `dify/README.md` 3.2 节的策略（先剥离 `<think>…</think>`，再从后往前逐个候选花括号对象尝试解析，取最后一个含目标键的合法 JSON）；
3. **工序 3 自检作为硬门槛**：变量集合与字段集合不一致就不允许启用，AI 的判断错误不会流到生成阶段；
4. **过程留痕**：Agent 的原始输出写入 `structure_meta_json`，便于复盘、调提示词、换模型后重跑。

**模型参数沿用项目既有约定**（见 `dify/README.md`「模型与参数约定」）：`name: deepseek-v4-flash`、`thinking: false`、`temperature: 0.1`（识别属抽取任务，要低温度）、`max_tokens: 4096`。End 需透出 `parse_error` 供后端识别解析失败，避免像现在的 `extract_template_variables` 那样静默返回空列表。

Agent 在**复核阶段**还有第二个用途（可作为后续增量）：用户在复核页说"漏了质保期字段""这个该是日期"，由 Agent 调工具改 schema 并给出解释。

### 2.3 工序 3：回写与自检（程序）

把确认后的字段落回 docx，产出**标准化模板**。回写规则按候选类型分：

| 候选类型 | 回写方式 |
| --- | --- |
| `form_field` 表单域 | **拆域**：删掉骨架 run（`fldChar` begin/separate/end 与 `instrText`），只把域结果 run 的文本换成 `{{ key }}` 并保留它的 `rPr`。域名的加粗/字体因此原样沿用 |
| `hash` `#...#` | 整段井号替换为 `{{ key }}`（含两个 `#`） |
| `jinja` 已有占位符 | 直接改名，纯文本替换 |
| `blank` / `label_empty` / `empty_cell` | 在落点处插入 `{{ key }}`（见下方跨 run 处理） |
| `sdt` 内容控件 | 保留控件外壳只换内容（对 Word 友好），整段替换 |

**只替换该替换的那一段**：`form_field` / `hash` 的落点是精确字符区间，所以 `甲方：PUR_BILL_TO_NAME` 只会变成 `甲方：{{ PUR_BILL_TO_NAME }}`。早期版本对含表单域的段落只出一个"整段"候选，回写会把 `甲方：` 和整句价格条款一起删掉——一份合同里一个段落能塞进 9 个变量，整段写等于把条款清空。同一段落有多个落点时，**必须从后往前写**：先写左边的会挪动右边那些落点的字符位置。

**同名变量写全所有落点**：字段带 `slot_id`，回写按槽位取出全部候选（首部 + 签署信息表、文本框 Choice + Fallback 副本），逐个写同一个 `{{ key }}`，生成时一处填写多处生效。

**跨 run 的处理（技术难点）**：Word 会把 `甲方：____` 拆成多个格式片段（run），占位符必须写进跨度中的**第一个 run**、清空其余 run 的文本，并让占位符**继承该 run 的 `rPr`**（字体、下划线、字号）。否则填出来的合同排版会走样，用户能看出"这是贴上去的"。实现思路沿用 docxtpl `patch_xml` 处理被拆散 `{{ }}` 的做法。

**含图形的 run 一律不碰**：给一个内含 `w:drawing` / `mc:AlternateContent` 的 run 赋 `.text`，python-docx 会把它的子元素全部清掉——实测这一步把整个浮动文本框（连同里面的合同编号、签订日期）删了。回写在挑写入目标时跳过这类 run。

**自检闭环（关键）**：回写完成后做四类断言，任一不过即标记失败、保留原始文件、不覆盖：

```
1. set(标准化模板解析出的变量名) == set(复核确认的字段 key)      # 变量齐全
2. 段落文本 == "原文按落点换成占位符"的预期文本                  # 跨度之外的文字逐字未动
3. 该消失的痕迹已消失（无 FORMTEXT 域残留、无 #...# 残留、下划线填空已替换）
4. 同一段落同一个键只出现一次（防落点重复把占位符写坏）
```

第 1 条只保证"变量都在"，会漏掉两类事故：占位符追加在下划线后面（变量齐了但填空没被替换），以及整段被替换（变量也齐了，但标签和条款正文都没了）。第 2 条把"只替换该替换的"从主观要求变成可断言的等式——它的算法与回写同源，所以对"落点重复导致写坏占位符"这类问题必须靠第 4 条兜住（实测遇到过：`candidate_ids` 与 `candidate_id` 指向同一处时会被写两遍）。

### 2.4 工序 4：人工复核（必须有）

导入后**不直接可用**，进入 `review`（待复核）状态。页面形态：

- **左侧**：标准化模板的 PDF 预览，能直观看到占位符插在了哪个位置；
- **右侧**：字段清单表格，可修改中文标签 / 控件类型 / 是否必填 / 默认值 / 排序，可删除误识别项，可手动新增漏掉的项。表格另有两列只读信息——**变量名**（模板原名 + 主体标签 + `×N` 落点提示）与候选类型的中文名，用来回答"这个字段是文档里哪一处、要不要一起改"。变量名不给编辑：它是甲方既有字段码，也是回写定位的依据。

确认后模板变为 `ready`（已启用），才出现在合同生成页。

这一步同时承担了原来缺失的「字段配置」职责，也让"模板改不了只能删了重传"的问题一并消失。

### 2.5 数据落库

`contract_templates` 需要同时保留两份文件并记录结构状态：

| 字段 | 说明 |
| --- | --- |

```
┌──────────────────────────────────┬─────────────────────────┐
│  [模板预览] [生成稿]      [下载] │  合同类型  ▾ 采购       │
│ ──────────────────────────────── │  合同模板  ▾ 钢材采购…  │
```

- **两级选择**：先选合同类型（读受控词表），再选该类型下的模板；去掉当前 `page_size: 100` 的硬上限，补搜索。

### 3.2 三层实时预览

| 层 | 时机 | 做法 | 目的 |
| --- | --- | --- | --- |
| 1 | 打开模板时 | 后端把标准化模板转成 PDF 并光栅化成逐页 PNG，前端出骨架 | 让用户先看到合同全貌与待填位置 |
| 2 | 用户敲字时 | **前端本地**把占位块替换为当前输入值，零请求零延迟 | 即时反馈，构成"实时预览"的主体 |
| 3 | 停止输入约 500ms 后 | 调一次后端**真实渲染**（带当前取值），返回新的逐页图片覆盖左侧 | 纠正前端本地替换搞不定的情况：`{% for %}` 生成的表格行、`Subdoc` 富文本、`{{ a.b }}` 属性访问 |

点"生成"后，左侧切到"生成稿"标签页显示终稿，保证"看到的 = 下载到的"。

## 4. 必须提前知道的工程坑

| 坑 | 说明与对策 |
| --- | --- |
| **LibreOffice 默认看不到系统字体 → 中文全部丢失（本机已实测复现并解决）** | 详见 4.1，这是会让整个预览功能报废的坑，必须按 4.1 的结论实现转换服务 |
| **LibreOffice 并发会失败** | 多个 `soffice --headless` 同时运行会因共享用户配置目录锁冲突而挂掉。必须为每次调用指定独立的 `-env:UserInstallation=file:///tmp/...` 配置目录，再加进程级信号量串行化，并设超时 |
| **预览需要缓存** | 模板预览按 (模板 id, 版本号) 缓存 PDF，否则每次打开页面都重转一遍，慢且浪费 |
| **回写的格式保留** | 跨 run 插入占位符时若直接改 run 文本会丢下划线/字号，必须显式继承 `rPr`，否则填出的合同排版走样 |
| **原始文件必须保留** | 识别结果不满意时要能重跑，不能让用户重新上传 |
| **HTML 预览的 XSS 风险** | 若将来启用"转 HTML 预览"路线，`v-html` 渲染前必须过 DOMPurify——HTML 来自用户上传的 docx，是存储型 XSS 入口。当前选定的 PDF 路线无此问题 |
| **AI 识别失败不得静默** | 工序 2 的 `parse_error` 必须回传前端并阻断"启用"，不能像现在的 `extract_template_variables` 那样吞掉异常返回空列表 |

### 4.1 LibreOffice 中文字体问题（2026-09-14 实测结论）

**现象**：`soffice --headless --convert-to pdf` 能跑通、能产出 PDF、文本层也正确（可搜索、可复制），**但中文在视觉上全部消失**。合同预览会是一份"只有数字和英文"的空白件。

**定位过程与结论**：用受控实验（同一段中文 + 三种字体各生成一份 docx 转换）确定：

| 文档声明的字体 | PDF 实际使用 | 结论 |
| --- | --- | --- |
| `Liberation Serif`（LibreOffice 自带） | `LiberationSerif` | ✅ 正常 |
| `Helvetica`（macOS 系统字体） | `LinuxLibertineG` | ❌ 被替换 |
| `Songti SC`（macOS 系统中文字体） | `LinuxLibertineG` | ❌ 被替换 |

即 **该 LibreOffice 安装看不到任何 macOS 系统字体，只认自带字体**（自带的 Linux Libertine / Caladea / FrankRuhlHofshi 全无中日韩字形，于是中文渲染为空白）。根因是 LibreOffice 使用**自带的 fontconfig 配置**，其中没有 macOS 字体目录——运行日志里可见 `Fontconfig warning: ... no <cachedir> elements found` 佐证。排除过的干扰项：非沙箱运行同样复现、移除 `com.apple.quarantine` 隔离标记无效、原文档未显式声明字体（走主题字体）不是必要条件。

**解决方案**：给 LibreOffice 指定一份包含系统字体目录的 fontconfig 配置（通过 `FONTCONFIG_FILE` 环境变量），实测中文即刻正常：

```xml
<?xml version="1.0"?>
<!DOCTYPE fontconfig SYSTEM "fonts.dtd">
<fontconfig>
  <dir>/System/Library/Fonts</dir>
  <dir>/System/Library/Fonts/Supplemental</dir>
  <dir>/Library/Fonts</dir>
  <dir>~/Library/Fonts</dir>
  <cachedir>/tmp/lo-fc-cache</cachedir>
</fontconfig>
```

转换后实测：`钢材采购合同模板` → 字体为 `STSongti-SC-Regular` / `HiraginoSans-W7` / `ArialUnicodeMS`，中文与版式均正常，单份转换约 2.5 秒。

**落到 `docx_convert.py` 的要求**（P0 已按此实现）：

1. 调用 `soffice` 时必须带 `FONTCONFIG_FILE`，**不能依赖环境默认值**；fonts.conf 由服务在运行时生成（字体目录可配置，便于容器替换），且 `<dir>` 与 `<cachedir>` **必须写绝对路径**——实测相对 cachedir 会让整份配置静默失效，症状与"没配 fontconfig"完全相同（见经验文档 6.1）。
2. 字体路径按平台配置化（macOS：上述系统目录，由 `PDF_FONT_DIRS` 覆盖；Linux 容器：装 `fonts-noto-cjk` 并指向 `/usr/share/fonts`）。
3. LibreOffice profile 每进程一个，**目录名带 fontconfig 指纹**（内容哈希）：profile 会缓存字体解析结果，配置变了不换目录会出现"改了配置不生效"（见经验文档 6.3）。
4. 转换后做**中文字形自检**：源文档含中文却检测不到墨迹时抛错并丢弃产物，不返回空白件。
5. 单次转换加超时（默认 120 秒），soffice 共用 profile 会锁冲突，因此进程内用信号量串行化。

### 4.2 预览不走前端 PDF 渲染（P0 实测结论）

即使 PDF 生成完全正确，**pdf.js 仍会把中文渲染成错位的 ASCII 字形**（`数`→`!`、`量`→`"`），且全程无 warning。同一份 PDF 用 MuPDF 渲染完全正常。因此预览链路改为：

```
docx --LibreOffice--> PDF --PyMuPDF 光栅化--> 逐页 PNG --HTTP--> <img>
```

- 后端两个接口：`GET /templates/{id}/preview`（页数与每页尺寸）、`GET /templates/{id}/preview/{page_no}`（PNG，带缓存）；
- 前端只做分页、缩放与滚动同步，不受浏览器字体处理差异影响；
- 代价：预览不能选中文字。换来的是跨平台稳定的中文渲染，同时省掉 1.3MB 的 pdfjs 前端包；
- PDF 仍然生成并保留，供后续"下载 PDF"使用。

> 细节与排查过程见 `docs/PDF中文字体渲染问题排查经验.md` 第 6 节。

## 6. 实施顺序

先做不依赖 AI 的部分，确定性能力可以立刻验证：

| 阶段 | 内容 | 前置依赖 |
| --- | --- | --- |
| **P0** ✅ | LibreOffice 转换服务（fontconfig / profile / 超时 / 串行 / 中文自检 / 缓存）+ 逐页图片预览组件 | 无（可独立验证，是后续所有预览的基础） |

| **P3** ✅ | 生成阶段改造（两级选择、schema 表单、必填校验、草稿预览、落库下载） | 依赖 P2 产出的字段 schema |

### 6.1 实际落地的接口清单

| 接口 | 说明 |
| --- | --- |
| `POST /templates` | 导入模板（保留原始文件，状态 pending） |
| `GET /templates/{id}` | 复核上下文：文档大纲 + 候选空位 + 识别留痕 |
| `POST /templates/{id}/structure` | 扫描 → Dify 应用六 → 回写 → 自检（状态转 review） |
| `POST /templates/{id}/fields` | 保存复核结果（重新回写 + 自检），`enable=true` 转 ready |
| `POST /templates/{id}/reset` | 回到待识别 |
| `GET /templates/{id}/preview` · `/preview/{page}` | 模板逐页图片预览 |
| `GET/POST/DELETE /templates/categories` | 合同类型受控词表 |
| `POST /generate/contract` | 生成合同：必填校验 → 确定性填充 → 落库 → 返回记录 ID |
| `POST /generate/contract/preview` | 按当前取值渲染草稿（内容哈希缓存，不落记录）——"填完即预览" |
| `GET /generate/contract/records` · `/{id}/download` · `/{id}/preview` | 生成记录列表 / 归属校验下载 / 终稿预览 |
| `DELETE /generate/contract/records/{id}` | 删除生成记录与产物 |

> 生成产物的下载地址从裸文件名的 `/generate/files/{name}` 改为按记录 ID 的
> `/generate/contract/records/{id}/download`，因为前者任何登录用户知道文件名就能下载他人产物。
> 规章制度生成（需求⑧）仍沿用 `/generate/files/{name}`，未在本次改动范围内。

> **软硬件前置（2026-09-14 更新）**：LibreOffice 已安装并验证可用——`LibreOffice 26.8.0.3`（`/Applications/LibreOffice.app`，`soffice` 已进 PATH，单份 docx→PDF 约 2.5 秒）。**但必须按 4.1 的结论配置 fontconfig，否则 PDF 中文全是空白**。项目尚未编写 `docker-compose.yml`，容器化时需在镜像内一并安装 LibreOffice（约增加 400–600MB）与 `fonts-noto-cjk`，并把 4.1 的 fontconfig 指向 `/usr/share/fonts`。
