## 意见 1：前端去掉「咨询类别」设定

**原始意见**：前端页面不要设置咨询类别，不应该有咨询类别的设定，就是用户咨询内容，然后 RAG 查询，回答就好。

**我的理解**：聊天页去掉顶部的「咨询类别」单选组（通用/差旅/接待/招采），交互简化为「提问 → 知识库检索 → 回答」。

**现状**：该类别目前是端到端串通的，涉及三处：

| 层 | 现状 |
| --- | --- |
| 前端 | `ChatView.vue` 顶部单选组，提问时随请求发送 `category` |
| 后端 | `ChatRequest.category` 合并进 `inputs` 传给 Dify |
| Dify | 「合规咨询」Chatflow 的 Start 节点有 `category` 变量，LLM 回答 prompt 中引用了 `{{#start.category#}}` |

**可行性**：可实现，改动量小。

**实施要点**：

1. **必须同时改 Dify 工作流**：删掉 Start 节点的 `category` 变量后，prompt 里的 `{{#start.category#}}` 会变成未定义变量导致流程报错，需一并删除该引用（改为不带类别的统一提示词）。
2. 前端移除单选组，仅保留「新建会话」。
3. 后端 `ChatRequest.category` 建议保留字段（向后兼容，不再注入 inputs）或直接删除；`_build_inputs()` 相应简化。
4. 改完需**重新导入「合规咨询」应用**（会产生新的 API Key）。

**待确认**：去掉类别后是否保留「新建会话」按钮？（建议保留）

## 意见 2：知识库管理界面支持「新建知识库」（**暂不实现**）

> **决策：暂不实现**（2026-09-14）。原因：新建的库不会被现有工作流检索到，必须在 Dify 控制台手工把新库勾进各应用的检索节点；
> 「建库 + 手工挂载」的链路价值/成本比不高。以下可行性分析保留备查，后续需要时按此实施。

**原始意见**：知识库管理界面应该有可以新建知识库的功能，你看看可以实现吗。

**结论：可以实现。** 但有两个结构性前提必须先解决，否则新库建出来也「接不上」。

### 可行性依据

Dify 服务 API 提供 `POST /v1/datasets`（必填仅 `name`，可选 `description` / `indexing_technique` / `permission` / `embedding_model` 等），用现有的知识库 API Key（`DIFY_API_KEY`）即可调用；同时提供数据集查询/更新/删除接口。

### 前提 A：知识库清单要从「写死」改成「可管理」

现在 5 个知识库是**硬编码**的：`.env` 里的 `DATASET_ID_LAW/REGULATION/CASE/RULE/EXPERT` + 代码里的 `DATASET_META` 字典（`services/knowledge.py`）。新建的库没有地方存。

需要：

- 新增本地表 `KnowledgeBase`（`key` / `name` / `dify_dataset_id` / `description` / `indexing_technique` / `embedding_model` / `created_by` / `created_at`）；
- 后端知识库读写从「固定 5 个」改为「查表」，现有 5 个库作为种子数据迁移进去（保持原有 `key` 不变，兼容存量文档记录）；
- `DATASET_ID_*` 环境变量逐步废弃（或在初始化时导入一次）。

### 前提 B：新建的库不会自动参与检索（重要）

Dify 工作流的**知识检索节点是写死 dataset_ids 的**：

| 应用 | 已挂知识库 |
| --- | --- |
| 合同审查 | 法律法规库、规章制度库、典型案例库 |
| 制度审查 | 法律法规库、规章制度库 |
| 合规咨询 | 规章制度库、专家知识库 |
| 规章制度生成 | 法律法规库、规章制度库 |

因此新建的知识库**默认不会被任何问答/审查流程检索到**，必须在 Dify 控制台打开对应工作流的检索节点手工勾选该库（或改 DSL 重新导入）。

**这意味着「新建知识库」目前更接近「新建一个可上传/维护文档的容器」，要真正参与问答还需一步控制台操作。** 可选方案：

- **方案一（简单）**：前端在建库成功后给出明确提示「新库需在 Dify 控制台挂载到对应应用后才参与检索」，并展示挂载位置说明；
- **方案二（进阶）**：建库时让用户选择「参与哪些应用」，后端通过 Dify 控制台 API 修改各工作流的检索节点 dataset_ids（需要控制台登录态/更高权限的凭据，实现与运维成本明显更高，且不稳定性更大）。

建议先做**方案一**，把方案二留作后续增强。

### 实施要点

- 后端：`dify.py` 增加 `create_dataset` / `update_dataset` / `delete_dataset` 封装（知识库归属用 `DIFY_API_KEY`）；
- 后端：`models/knowledge_base.py` + `services/knowledge.py` 改造从表读取；接口 `POST /knowledge/bases`、`PATCH /knowledge/bases/{key}`、`DELETE /knowledge/bases/{key}`；
- 前端：知识库页加「新建知识库」对话框（名称、描述、索引方式、embedding 模型），列表从固定 5 项改为动态；
- 运维注意：
  - **删除知识库会连带删除其下所有文档（Dify 侧不可恢复）**，必须二次确认并校验非内置库；
  - embedding 模型需与现有 5 个库保持一致（当前为 SiliconFlow `BAAI/bge-m3`），否则跨库检索与 rerank 效果不一致；
  - 建库后需要等 embedding 模型校验通过（Dify 会校验模型可用性）。

## 意见 3：生成相关页面拆分为独立页面

**原始意见**：合同生成和规章制度生成应该是两个页面；合同生成那个页面有两个功能：合同模板库导入 和 合同生成。

**确认后的决策（2026-09-14）**：进一步拆为**独立页面**——「合同模板库」与「合同生成」各占一个页面，「规章制度生成」独立页面。

| 菜单 | 路由 | 页面内容 |
| --- | --- | --- |
| **合同模板库** | `/templates` | 模板 .docx 导入、按合同类型分类、查看模板占位变量、下载/删除 |
| **合同生成** | `/generate/contract` | 选模板 → 填变量 → docxtpl 填充 → 预览/下载 |
| **规章制度生成** | `/generate/regulation` | 需求 → 大纲（可编辑确认）→ 全文 → 自动合规审查（最多 3 轮修正）→ 预览/下载 |

**现状差异**：现在 `/templates` 与 `/generate` 都是骨架，且菜单里只有一个「文档生成」入口。

**可行性**：可实现，属于页面组织调整，不涉及新增能力。

**实施要点**：

1. 路由与菜单：新增 `合同生成`（`/generate/contract`）与 `规章制度生成`（`/generate/regulation`），删除独立的 `/templates` 页与菜单项（模板管理作为合同生成页内的区域/对话框）；
2. 后端接口保持分离（模板 CRUD 与生成分开），前端在同一页聚合调用；
3. 需同步修改设计文档 `§6 需求⑥ 合同模板库`、`§7 需求⑦ 合同生成`、`§8 需求⑧ 规章制度生成` 中的「前端页面」归属描述；
4. 依赖项：⑦ 合同生成依赖 `docxtpl` 模板填充（`services/word_generator.py` 已有 `render_template`），⑧ 需要补 `build_docx_from_sections()`（python-docx 程序化排版）。

**待确认**：模板库导入在页内是「独立区域」还是「弹窗」？（建议页内上方区域 + 列表，与生成表单并列，操作路径最短）

## 意见 4：内容纠错不单独建页，改为专家在合规咨询回答上直接标注

**原始意见**：内容纠错不应该单独生成一个页面，应该是专家用户针对合规咨询相关的回答直接引用标注。

**我的理解**：去掉 `/correct` 独立页面；在聊天页每条 AI 回答上提供「标注/纠错」入口，**仅专家角色可见**，专家就地提交修正内容，直接写入「专家知识库」，后续 RAG 回答即引用该标注。

**与需求原文的一致性**：需求⑤原文是「对于大模型输出的答复，可由指定权限的人员进行内容纠错」——就地标注才是它最自然的形态；原设计里那个「纠错记录工作台页面」属于过度实现。

**可行性**：可实现，但**依赖真实登录与角色体系**（当前登录是骨架，任意账号可签发）。

**实施要点**：

1. **角色与权限（前置依赖）**：`api/auth.py` 接 `passlib`/`bcrypt` 密码校验 + 种子账号（`expert` / `user`）；JWT 携带 role；`deps.py` 把 `require_admin` 占位换成 `require_expert`；前端按角色控制按钮可见性。
2. **就地标注 UI**：聊天页 AI 回答气泡下方加「标注」按钮（专家可见）→ 弹窗展示原回答 + 修正内容输入 → 提交；
3. **接口**：`POST /corrections`（携带 `conversation_id`、`message_id`、原回答、修正内容）→ 调用 `create_by_text` 写入专家知识库 → 落库 `CorrectionFeedback`（`write_status`: written/failed，失败可重试）；
4. **message_id 串联**：Dify 的 `message_end` 事件已返回 `message_id`，后端 SSE 已透出（`event: message_end`），前端目前只用了 `conversation_id`，需补存 `message_id` 以便标注时精确定位到某条回答；
5. **删除** `/correct` 页面与菜单；标注历史可在聊天页弹窗内查看（或专家个人中心），不再单独开页；
6. **闭环验证**：写入专家知识库后，「合规咨询」检索已挂该库 → 下次问答即参考专家修正内容（需求⑤闭环）。

**待确认**：
- 是否同意为这一条先落地**真实登录（密码校验 + 种子账号）**？这是专家权限的唯一门槛，也是需求⑤的前置。
- 「引用标注」是否还需要在回答上显示一个「已被专家标注」的标识与标注历史入口？（建议要，便于专家回看与纠错追溯）
